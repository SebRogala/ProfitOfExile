# Desktop App Library (`$lib`)

Component registry for the ProfitOfExile desktop app. Read this first before creating or modifying components.

## Stores

| File | Export | Description |
|------|--------|-------------|
| `stores/status.svelte.ts` | `store`, `initStatusStore()` | Shared app state — event-driven from Rust backend. No polling. Call `initStatusStore()` once from root layout. Read `store.status` and `store.logs` reactively. That call also owns the entitlements + update-check pair. `loadEntitlements()` is FIRED, never awaited: it retries an unreachable server for the life of the app, so awaiting it would hold the app's boot — and this call's cleanup handle — behind a network that may never come up. The 30-minute poll is therefore armed unconditionally; each run of it re-asks for entitlements (so a device promoted on the server picks its grant up without a restart) and waits at most `ENTITLEMENTS_FIRST_CHECK_WAIT_MS` (10 s) for that answer before checking through `$lib/updater/check`, because the channel decides which manifests get asked but must never decide WHETHER the check happens. |
| `stores/ssot.svelte.ts` | `ssot`, `startSsotStore()`, `stopSsotStore()`, `fetchSsot()`, `applySnapshot()`, `setNormalVariant()`, `setDedicationVariant()`, `setDedicationPool()`, `setDedicationSelection()`, `setModuleEnabled()`, `setMercSourcesOff()`, `setTempleKeys()`, `setTempleConfig()`, `setTempleProfile()`, `rearmTemple()`, `templeDebugCapture()`, `SsotSnapshot`, `ScreenSlice`, `ScreenScaleSource` | Rust-owned single source of truth, polled every 3000 ms (`ssot-changed` is only an eager nudge — never trusted as the payload). Read `ssot.league` / `ssot.normalVariant` / `ssot.dedicationVariant` / `ssot.dedicationPool` / `ssot.modules` reactively; write through the exported setters (never assign the fields directly or keep a local copy). Market fields and module flags carry a poll-vs-write ordering guard; the two module SLICES do not, because nothing here writes them. `ssot.mercenary` (POE-165) is the Merc OCR slice — status, last capture, learned templates, last error, geometry source, and the POE-199 enabled-guide echo `sourcesOff` (its one writer, `setMercSourcesOff`, goes through Rust and re-fetches, like the temple setters). `ssot.temple` (POE-171) is the temple builder slice — status, layout, side panel, advice, mode, and the settings echo (`keys` / `config` / `profile`). Both are read-only and apply the same way: a snapshot carrying the slice replaces it WHOLE, one lacking it leaves the last known one standing. The five `temple*` writers go through Rust commands that write `temple_settings`; Rust echoes the accepted value onto the slice and the setter re-fetches, so there is no optimistic local value. They return the rejection message (`string | null`) instead of throwing, and a rejection also reaches `app_log_from_frontend` — Rust VALIDATES these, unlike the market setters whose only failure is IPC. `snapshot.screen` (POE-214) is the third Rust-owned slice: the captured screen's `width`/`height` in physical px, the `uiScale` measured on it, the `source` that measured it (`"merc-frame"` / `"merc-ocr"` / `"remembered"`), `measuredAtMs`, `verifiedThisSession` (POE-240 — a verifying cue produced this value in THIS run; false means trusted from last session, and it is never persisted), and — POE-237 — `monitorId` plus `origin` (`[x, y]`), the DISPLAY it was measured on and that display's top-left in virtual-desktop physical px. `monitorId` is a Win32 `HMONITOR` truncated to 32 bits, is NOT comparable with anything `availableMonitors()` reports (which is why `overlay/monitor-choice.ts` matches a display on its position), and `0` means unknown — a scale persisted before POE-237 — so it is never compared as an identity without excluding `0` first. **Its unit is game-UI px per px of the reference fixture** — a 1920x1200 screen is 1.0 by definition and 1080p measures 0.90 = 1080/1200, because the game's UI scales with screen HEIGHT. That is NOT the temple's `AnchorCalibration.scale` unit (relative to its own 1374-px reference width) and the ratio between them is unmeasured, so the two numbers must never be substituted for each other. **The merc detect tick is the sole writer** (Rust `ssot::publish_screen`, one measurement per tick, emitted only when the resolution, the source, or the scale (by ≥ 0.01, above the per-tick fit wobble) actually changes); there is no rank between sources: the label is a statement about the cue, and `ssot::accepts` reads it to refuse a `merc-ocr` reading that only re-states a standing `merc-frame` value (POE-240) — unless it comes off a DIFFERENT display, which no drift band can explain (POE-237). Its one webview consumer is the Settings "Screen geometry" card (POE-227), which displays it and offers Recalibrate. Of the two READERS named in POE-214, the Lab `CaptureRegion`s now read it (POE-233 — the gem and font rects are reference rects scaled by `uiScale`, resolved per scan iteration so a mid-session measurement takes effect, and a rect the user placed in Settings still wins); the temple is still to come, once its unit ratio is measured. Its lifecycle is normative and lives in "Screen Geometry (SSOT)" below. `null` (the key is always present) means nothing has measured a screen, and a consumer must NOT read it as 1.0. `merc-geometry.json` is unrelated to any of this: it is the user's debug seam for overriding the merc grid constants, not the scaling path, and editing it un-measures the matcher (see the merc OCR section below). `setModuleEnabled()` is the ONE module writer and always persists: nothing forces a module flag on the user's behalf, because the widget-config flow raises the overlay WINDOW instead of the module (POE-241 — arranging widget positions starts no module work, so no non-persisting variant is needed). |
| `stores/navigation.svelte.ts` | `nav`, `viewToPath()`, `parseView()`, `VIEW_PATHS`, `View` | Global view toggle. `nav.view` is `'lab' \| 'settings' \| 'dev' \| 'mercenaries' \| 'temple' \| 'currency-exchange'`. All pages are always mounted (hidden via CSS) — do not use SvelteKit routing for main views because it unmounts their listeners. `viewToPath(view)` gives the Sidebar path for a view (`'lab'` → `'/'`); use it instead of re-deriving the mapping, and add a `VIEW_PATHS` entry when adding a view — `go()` inverts that table, so there is no second mapping to extend. The pick is the persisted `navView` pref (ADR-013), so the app reopens on the last tool: `nav.view` is a GETTER over the pref (validated on read through `parseView`, unknown → `'lab'`) and `nav.go(path)` writes it — never assign `nav.view`. Restore-on-launch and "a click made before the prefs load lands beats the stored value" both come from `persisted()`'s own dirty-flag semantics, not from a restore step here. |
| `stores/entitlements.svelte.ts` | `entitlements`, `hasFeature()`, `loadEntitlements()`, `normalizeEntitlements()`, `MERC_FEATURE`, `EXCHANGE_FEATURE`, `TEMPLE_FEATURE`, `Channel`, `Entitlements` | What the server says THIS device may see (POE-203). `GET /api/device/me` answers `{ role, channel, features[] }` for the device identity POE-102 already attaches to every request, and the `X-Device-ID` header IS the question — a load made before `get_status` delivered a device id does not fetch at all, because the server answers 200 for an anonymous device and that answer would settle the store on "entitled to nothing". A device-less or failed attempt is therefore not-yet-loaded rather than an answer: it backs off (`RETRY_DELAYS_MS` — 5 s, 15 s, 60 s, then every 5 min) and asks again until a device-identified answer lands, and concurrent callers share one chain. `initStatusStore()` calls it at startup and again on its 30-minute tick. Read `entitlements.channel` (drives which update manifests `$lib/updater/check` asks) and `hasFeature(MERC_FEATURE)` / `hasFeature(TEMPLE_FEATURE)` / `hasFeature(EXCHANGE_FEATURE)` (each drives every surface of its module — Mercenaries, Temple of Atzoatl, Currency Exchange). **Hiding, not securing**: every gated module ships in every build and this only decides whether the app draws it. The default is stable with NO features, both before the answer arrives and after one that never does — a failed fetch logs a warning and shows the user nothing, so every launch has a window in which an entitled device looks unentitled, which is why no gate anywhere writes a preference. `normalizeEntitlements()` is the pure narrowing: only the literal `"beta"` selects the beta channel and only string entries survive into `features`, because an answer the client cannot read must grant nothing. |

| `overlay/widgets/widget-geometry.ts` | `WidgetGeometry`, `WidgetRect`, `WidgetPlacement`, `HostSize`, `ResizeEdge`, `BASE_EDGE`, `MIN_WIDGET_SIDE_CSS`, `EDGE_CURSORS`, `cssRect()`, `widgetGeometry()`, `clampToHost()`, `edgeAt()`, `edgeFor()`, `seedRect()`, `sizeToPersist()`, `dragged()`, `resized()`, `rebase()`, `placementFor()` | Every number `WidgetHost.svelte` decides, split out because an overlay window has no test harness — the same split `content-height.ts` and `hot-rects.ts` use. The quality GATES (POE-191, `Gates`/`GateInputs`) are SEVEN since the divine trash-price knob of 2026-08-23, and five of them ship OFF: `gateDefaults` is five zeros plus `minItemPrice: 0.5` and `minItemPriceDiv: 0.4`, and `applyGates` guards every comparison with `> 0` — `maxTickPct` included, a ceiling of zero being a market with no spread at all — so 0 is a genuine off for each of the seven and no `Infinity`-style sentinel is needed. `minItemPrice` is the CHAOS TRASH-PRICE knob (POE-196) and one of the two default-on filters in the app: it drops a play whose `investment` — the wire's per-unit chaos cost of entering ONE exchange, always chaos and the same field for a 1-hop route as for a direct one — is under 0.5, which removes the bottom of the sub-chaos tier (Clear Oil and its neighbours) from the out-of-the-box table. ADR-017 bars a default from hiding a live market and names this the first of its two sanctioned exceptions, on an ABSOLUTE-SIZE argument and not a spread one: the predicate never reads `tick`, a sub-chaos market quotes as finely as any other, and the claim is only that an entry under half a chaos pays too little per flip to be worth the repeats, so those rows crowd out the ones the reader would act on. The 0.5 is the owner's call (2026-08-22) and is set where it is because ADR-015's motivating example was Sacrifice fragments at ~0.2–1c — a 1c floor would have hidden by default the flips that ADR moved the gates client-side to rescue. It is inclusive on the passing side like the other six (exactly 0.5c is kept, only cheaper is dropped) and never reads the SCALED investment — that is the Run cost bounds' question. `minItemPriceDiv` is its DIVINE TWIN (owner ruling, 2026-08-23) and the second default-on filter: it judges a play ONLY when the buy leg's `quote` is `DIVINE_ID` — the entry currency, `legs[0]`, so a chaos-quoted row is never touched by it however cheap it is — and it compares `play.investment / divineChaosRate`, the SAME per-exchange entry cost the chaos knob reads, un-converted by the rate the server valued it with. Deliberately not the buy leg's own divine-denominated `price`, which needs no rate but is the hour's printed EXTREME while `investment` is the UNDERCUT entry: the two knobs are one line drawn in two currencies and must not judge two price bases, and rebuilding the undercut as `price × (1 + tick)` would re-derive a market number this file does not re-derive. At 0.4 div it removes the hundreds-per-divine tier, where the whole edge is an undercutting war inside one price step; ADR-017 names it the second (and last) sanctioned exception on the same ABSOLUTE-SIZE argument as the first. A rate of 0 leaves every play unjudged rather than dividing by zero — an hour with no divine/chaos trade serves no divine-quoted play anyway. The two disarm separately, and `applyGates` takes the rate as a third parameter rather than a `Gates` field, so a response moving cannot make `movedGates` badge the row. `parseGate` reads blank OR unparseable as the knob's DEFAULT rather than hard-coding off, which is what lets a build change what unset means without rewriting a reader's settings file (`gateDefaults` is the one owner its three callers share: the parser's fallback, `resetGateInputs` behind the bar's Defaults button, and `movedGates`, the badge's verdict); the two armed knobs make that load-bearing rather than academic, since hard-coding 0 would ship the trash tier to every reader who never typed a level, and blanking either box therefore RESTORES that build's floor rather than turning it off. `0` typed explicitly survives parsing — the only way to disable a trash knob — and a negative reads as off too (a floor under the server's positivity floor could never fire, and `investment` is a cost and never negative; a negative ceiling would empty the table, so off is the recovery). `movedGates(gates)` is what the bar badges its collapsed row with: knobs MOVED off the shipped default, not knobs armed — the two stopped being one fact in POE-196, and a reader who types 0 into either trash knob is counted, because the badge says the table is not showing this build's answer. `snapGateInput(raw, fallback)` is the blur decision the bar's gate boxes read — `null` leaves what the reader typed, a string is written back — and it answers `''` rather than the default's digits for text that does not parse: writing `String(parseGate('abc', 0.4))` would put `0.4` in the box AND in the settings file, freezing that knob on this build's number, which is the drift the empty-string persistence exists to prevent and which only became reachable when a default stopped being 0. It lives here rather than inline in the bar because a `.svelte` file has no unit-test harness in this repo. POE-191 shipped these armed at the levels the server used to enforce — 3 chaos each / 10,000 c/h turnover / 10% max step / 5× step / 2% return — and POE-193 turned them off because the ranking now judges quality on a measured expectation and flags what it cannot stand behind, so an absolute cutoff in front of it hid measured-real plays (2026-08-21: 142 of 143 served 1-hop plays, and an 8,532 c/h flip against the 10,000 line). Those levels stay documented as the RECOMMENDED tightening, in the `gateDefaults` comment and in each knob's tooltip; typing all five reproduces the pre-POE-193 table, which `filters.test.ts` asserts both ways. Neither trash-price knob is one of them — the server never had a price floor in either denomination, so both exist on this side alone and have no Go counterpart to agree with. The numeric bounds are off by construction rather than by default — they have no default to consult, because the reader typed one to answer a question and an empty box means they are done asking. `applyGates` is still its own pass rather than seven more fields on `applyNumericFilters`: the two halves are set and unset by different controls (the gates have their own Defaults reset and their own explicit `0`; Clear sweeps the bounds and leaves the gates where the reader put them). `minRoiPct` is the last gate and NOT a `NumericFilters` field any more: it keeps its original persisted key, and `''` means off like the other four that ship off. `maxTickPct` and `minRoiPct` are the only percent-vs-fraction crossings in the gate pass; `minEdgeTickRatio` is a bare ratio against a fraction and crosses nothing. The numeric bounds (`NumericFilters`, slimmed to `investMin`/`investMax`/`unit`/`divineChaosRate` — the gain bound went with the Quantity stepper, POE-192) arrive as the raw persisted strings — `""` is "filter off", not 0 — and are compared against the play's WORTHWHILE SCALE: the question a bankroll asks is what the run ties up until it pays, and since the app now derives that size, the figure the bound meets is `worthwhileScale(play).investment`, with the per-exchange `investment` as the fallback for a play that has no derivable scale — since POE-193 that is `expectedRoi <= 0`, a LIVE case rather than the impossible one the old `roi <= 0` reading guarded (ADR-015's floor governs `roi`; a measured expectation may be negative and ADR-016 serves it). Falling back is therefore a deliberate choice: dropping such a play here would be an eighth quality gate hidden inside a bankroll bound, and hiding the measured losers is what serve-and-flag exists to prevent. The asymmetry it buys is accepted and named — a losing play is judged by what ONE exchange costs while every other row is judged by what its whole run ties up, so a ceiling can keep a negative-expectation play it would have dropped had the play been worth repeating. Every GATE that reads a return stays on the BEST-CASE `roiPct`/`roi` for the same POE-193 reason the ranking left them (neither trash-price knob reads a return at all, so the choice does not arise for them): the levels a reader arms were calibrated against those two fields, and re-pointing one would silently change what a typed level cuts. Changing what the bounds MEASURE is why the page stores them under new `currencyExchangeScaleInvest*` pref keys — a ceiling typed against the old per-exchange meaning must not silently empty the new table. The `divine` unit converts the bounds, never the play, and a rate of 0 falls back to chaos rather than multiplying every bound to nothing. `matchesSearch(play, query)` (POE-190) is the view layer over those rules: a case-insensitive substring over the DISPLAY names of both halves of every leg — never the `Metadata/Items/...` ids, which are not on screen to explain a hit — with an empty or whitespace-only query matching everything, so a cleared box is a filter that is off rather than one that empties the table; it trims and lowercases per play so the signature stays a predicate the caller can hand the raw input to. `itemUniverse` lists only what the current response's plays are made of — the client is never sent the server's full asset. Tests live in `exchange/filters.test.ts`. |

## OCR Lifecycle

Two decoupled scan loops, each on a dedicated OS thread (required by Windows COM/WinRT).

Every crop is contrast-stretched and upscaled 2× before recognition (`capture.rs::preprocess_for_ocr`) — no size gate: crop dimensions say nothing about the glyph height inside them, and a font panel region widened for a high-resolution client was the case an earlier height gate skipped. The recognizer is pinned to en-US because the PoE client renders English whatever the Windows profile locale says. When that pack is missing, each scan thread falls back to the profile language and OCR degrades silently, so the warning is cached process-wide (`ocr.rs`) and surfaced as `AppStatus.ocr_language_warning` — the engine itself is thread-local and `build_status` must never resolve one. Every scan thread emits the status once when it starts and finds a warning cached, rather than only the thread that cached it: a debug command can resolve the engine first and has no status to emit, and the scan's own pre-spawn emit runs before any engine exists.

### Gem Tooltip OCR

Scans the gem tooltip region to detect transfigured gem names for the comparator.

**Start triggers** (all: clear comparator, restart scan):
- `FontOpened` — Client.txt `InstanceClientLabyrinthCraftResultOptionsList recieved` (fires on font open AND on CRAFT click — see Game UI facts below)
- Manual "Start Scanning" button

**Stop triggers**:
- 3 gems detected (auto-stop)
- 45s timeout
- ZoneChanged (left area)
- Manual "Stop Scanning"
- Next start trigger (bumps generation counter → old scan exits)

**Key behavior**: Aborts immediately if gem name list is empty (server unreachable). Uses `AtomicU64` generation counter for clean cancellation — no thread cleanup needed.

### Font Panel OCR

Scans the font region to capture craft options (transform, quality, experience, etc.) from the CRAFT screen.

**Start**: Izaro death voiceline (`LabFinished` nav event) — triggers when final Izaro is killed, right when the font becomes available. A `FontOpened` event also starts a scan whenever the liveness token (`font_scan_live_gen`) reads 0, so the panel is still read when `LabFinished` was never seen — the app launched mid-run, or the scan was stopped earlier by a zone change or lab exit.

**Running**: Scans at 250ms, parses options via `font_parser`, then union-merges the frame into the current round's option buffer (`merge_options`). A torn frame never deletes an option an earlier frame of the same panel read, and a value already read is never downgraded to `None` or overwritten by a disagreeing later read.

**Round tracking**: the panel's "Crafts Remaining" count owns the round boundary (`font_ledger`), gated on a `FontOpened` counter. `FontOpened` seals nothing — it fires on font open as well as on CRAFT, an unbounded number of times per craft. A count change with no `FontOpened` since the last accepted count is a misread: the frame's options still merge, the count is ignored. A count change after a `FontOpened` that holds for 2 consecutive frames seals the current round under the *old* count and opens the next one; direction is irrelevant. Known limitation: a round on screen for under 2 frames (~500ms) is never accepted, so its options fold into the neighbouring round.

**Stop**: a `font_scan_generation` bump — ZoneChanged, `LabExited`, a replacement scan, app shutdown — or 10 minutes with no active font panel on screen. There is no wall-clock timeout: a font run has no bounded length (stash trips, town portals, a player reading the options), and a scan expiring under a still-open panel silently lost every remaining craft. The idle limit measures from the last frame that saw the panel, so it only fires on a scan with nothing left to read — it is the backstop for a run whose stop event never arrives (the game killed rather than exited, the font never opened, screen capture failing in a loop). That path sends the session itself; every other stop is either a sender or is followed by one.

**Re-arm**: the token is what makes that restart exactly-once — a scan claims it on spawn and releases it on exit with a compare-exchange, so a superseded loop cannot clear its replacement's claim and a `FontOpened` arriving mid-handover does not stack a second loop. The case that needs it most is a portal trip out of the lab: `LabFinished` never fires again on return, so without the re-arm every remaining craft is lost. Every stop that can have rounds behind it sends and resets the session before a re-arm can run: ZoneChanged does it on the send path (and fires on the same log line as `LabExited`, which only stops the loop), idle expiry does it from inside the loop. So a re-armed scan is always a new segment; a mid-font town trip therefore reports one run as two font-session POSTs.

**Data flow**: ZoneChanged sends accumulated session (all rounds with options + crafts_remaining) to server via `POST /api/desktop/font-session`.

### Merc Recruit-Window OCR

A third loop (`src-tauri/src/mercenary/run.rs`), on its own thread for the same COM reason, and the only one that is **trigger-only** — it runs no OCR of its own accord (POE-198).

**Start triggers** (two asks, and they buy different looks — POE-204 WI-C):
- a Client.txt dialogue line whose speaker is shaped `<Name>, <joiner> <Epithet>` — one whitespace-free name, a comma, one ALL-LOWERCASE joiner word, a non-empty epithet — and is not on the NPC denylist: the mercenary's voice line, delivered by the ONE log watcher in `lib.rs` (never a second tailer)
- the page's **Scan now** button (`merc_scan_now`), for a window that was already open

**The voice-line gate** replaced POE-198's ten-second burst, because a mercenary speaks on APPROACH as often as on click and most lines are for a window nobody opened. A line arms the gate; the gate spends **two probes and then stands down**. A probe (`run::probe_tick`) is not a detect: it OCRs an anchor band (`geometry::probe_band_bounds` — the last row, the footer strip under it, one pitch of slack; `[650, 900, 651, 240]` on the 2026-08-24 1920×1200 dump, 7% of the screen) and accepts only on `is_button_line` — TAKE ITEM / REMATCH, exact equality after normalisation. `detect`'s other anchor, the wager line, is deliberately NOT a probe predicate: it sits above the grid and every band a probe can read starts at or below it. Probe 1 at **+500 ms from the line**, probe 2 at **+1.5 s from the line** — or `PROBE_GAP_MS` (1 s) after the first probe actually ran, whichever is later, so a gate that could not probe while the player was alt-tabbed looks once on their return and once a second after, rather than spending both on one frame. Then `Merc: no recruit window after <name> — standing down` and nothing more. A session that has never measured a panel uses `geometry::default_probe_band` (full width, the bottom 55%). That fraction is slack against an unknown, not a derivation: the buttons sit at 0.816 H in the one dump there is, and how the panel is anchored across resolutions and UI scales has never been measured. The retry always widens to the default band so a MOVED window is not a silent stand-down. A probe that finds the chrome hands its own grabbed frame to `detect_tick` in the SAME iteration, so a hit never waits a cadence.

**Two rules the gate is worded around.** A voice line arriving while a capture is HELD (`trigger::capture_held` — status `live` or `done`) is ignored outright: no arm, no announcement, no resumed read (a debug-only log line records it, because a chattering mercenary produces one per line). MEASURED 2026-08-26 09:41:56 — the arm resumed the paused read, the resumed cadence spent its first tick on a tooltip-covered frame, and "window gone" was published over a window that was plainly open. `capture_held` reads the PUBLISHED status off the watcher thread, so the loop also calls `trigger::disarm_probe` on every live tick — a line landing between the capturing detect and its publish would otherwise arm a gate nothing ever probes, and print a stand-down ten seconds later for a window on screen. And **Scan now bypasses the gate**: it asks for one detect, gets it the first moment the game is in front, and over a held capture does exactly one thing beyond that — a re-detect off the cadence, cropped to the panel when one is known (`LoopState::resume`, then `detect_tick`).

**A second line RE-ARMS the gate** with two fresh probes from its own clock. That is deliberate — the approach line and the click line are two lines, and it is the click that opens a window — so a chattering mercenary does keep buying looks. Two rules bound it: `LINE_STALE_MS` runs from the FIRST line of an unbroken chain by the same speaker, so continuous chatter still stands the gate down after 10 s; and the band widens on the second LOOK of the arming (`BurstGate::looks`, monotonic across re-arms) rather than on the second probe of some line, so chatter cannot pin the probe to a remembered rect the window may have moved out of.

**Timing is measured from the LINE, not from delivery.** `trigger::line_timestamp_ms` reads the `2026/08/24 22:51:12` stamp the line carries and `arm_at` backdates the gate to it; `log_watcher` can be up to 5 s behind (its `recv_timeout` fallback), and a 500 ms probe measured from delivery would be five and a half seconds after the click. The stamp is LOCAL time with no zone against a UTC clock, so it is believed only inside `[now - MAX_BACKDATE_MS, now]` — outside that band the gate falls back to the delivery clock, which is wrong by at most one hop, rather than to a skew that would fire both probes at once or leave them never due.

**Running**: both probes fire only while the game is the foreground window (the RAW `game_in_foreground`, not the held `game_focused`). A tick that CAPTURES or REFRESHES a window disarms the gate — never mere `LoopState.live`, which is still true after the first of the two misses that retire a capture. From there the live behaviour is unchanged (re-detect 2 s, hover-confirm 400 ms, retire after 2 misses), and retirement drops the loop back to waiting. `LoopStep::Waiting` is the armed-but-not-due state and naps one 100 ms quantum rather than the 250 ms `IDLE_NAP`, so a 500 ms probe is not served at 750 ms.

**Stop**: detection, or a stand-down. Three of those and each is worded apart, because they send the reader to three different places: the gate spent its LAST probe and found nothing (`StandDown::Probed`, the design's normal ending and the only one that is a verdict about the screen), the chain went stale with probes still unspent (`Stale`, `LINE_STALE_MS` 10 s — the game was not in front when they came due, a focus problem and not a detection one), and a **Scan now** whose alt-tab never came (`Manual`, bounded by `MANUAL_ARM_GRACE_MS` 60 s). The split is on WHY the gate ended, not on whether any probe ran: a gate that looked once and then lost the foreground reached no verdict, and reporting it as `Probed` would claim one. One `app_log` line per gate armed and one per gate that stood down; never one per tick, and never one per probe outside debug mode.

**The support vocabulary and its families** (`src-tauri/src/mercenary/vocab.rs`, mirrored by the generated `internal/mercenary/families.go`): both sides derive their family list from ONE committed file, `lib/mercenaries/__fixtures__/mercenary-stats.json` — GGG's own `Mercenary` block of `/api/trade/data/stats`, never hand-edited. A support's display text becomes its icon FAMILY in three steps, in order: strip the trailing ` (Tier N)`, strip a leading grade word (`Lesser `/`Greater `/`Gilded `), then fold the result through the family alias table. `Lesser Chain (Tier 1)`, `Chain (Tier 2)` and `Gilded Chain (Tier 3)` are three tiers of the one family `Chain`. The **alias table is the only place two different display names become one family**, and it is a CLOSED LIST of whole names rather than a prefix rule: `Increased Angle` is a real Gilded-only support with no `Angle` sibling, so a generic `Increased ` strip would key its cells under a family the vocabulary does not carry. It holds one entry today (POE-211) — GGG names one support's tiers `Lesser Increased Area of Effect (Tier 1)`, `Increased Area of Effect (Tier 2)` and `Greater Area of Effect (Tier 3)`, so the grade strip alone derived TWO families out of one support and filed the same art under two keys, which the learn-time refusal below then makes permanently unmatchable. Because the server validates uploads against its copy of this list, a change that SHRINKS it ships server-first (docs/DEPLOY.md → *Desktop <-> server ordering*).

**Icon signature, format 2** (POE-207, `src-tauri/src/mercenary/icons.rs`): a support cell reduces to its ALIGNMENT WINDOW — the inner crop (`inner_rect`) shrunk by `SHIFT_MAX` 3 SCREEN px per side, never scaled, so 33×33 at the live 0.974 scale and 34×34 on the 1:1 reference fixture — resized to 24×24 RGB (Triangle filter), with every position whose PIXEL CENTRE falls outside a 0.36 × 24 disc or inside the 0.45 × 0.35 tier-badge corner masked out (219 kept positions, 657 channels), then one zero-mean unit-stddev normalisation applied JOINTLY across those 657. The stored and wire form is the full 1728 bytes with the masked positions zeroed, so a reload reproduces the signature byte for byte. `normalize_cell` is the ONE place that derivation lives, because three things must agree on it byte for byte: what `learn` stores, what goes on the wire, and what the server derives (`internal/mercenary/signature.go`). Grayscale was format 1 and could not be tuned into working — the gold frame every cell shares dominated the luma, so visibly different families correlated 0.97–0.99 and `Matched` was unreachable for half the store (measured on 61 templates, 2026-08-26); colour plus the disc drops the genuine cross-family maximum to 0.818.

**Matching slides the CELL, not the template.** The rects `geometry::detect` emits land 1–3 px off per cell, and the same art in two cells scored 0.45–0.70 unaligned — under `icon_low`, so a cell the store already knew still read as unknown. `cell_candidates` builds the signature at all 49 shifts in ±3 px once per occupied cell, and `match_family` searches them in two stages, because the plain search is 49 × templates × 657 MACs — 1.8 G at the 792-sample pool ceiling, which does not fit a 2 s tick. Stage one scores every template over the nine coarse alignments (`dx,dy ∈ {−2,0,2}`); stage two rescores over all 49 both the top `REFINE_K` = 12 templates and the top 12 among families OTHER than the coarse winner's. That second half is not an optimisation: a coarse score is a maximum over nine alignments and UNDER-estimates the 49-alignment truth, so refining only the leaders would weigh an exact winner against an under-estimated runner-up, inflate the lead, and promote a `LowConfidence` cell to a confidently wrong `Matched`. What `learn` stores and the pool receives is the UNSHIFTED signature — storing the aligned best would carry this capture's jitter into every later comparison. The thresholds are unchanged (0.88 / 0.78 / 0.05) and now attainable, so one confirm on one cell resolves the same support wherever else it sits in the panel.

**The format bump is a purge, not a migration.** `purge_stale_store` runs at module start inside `writing_icons_dir` and BEFORE the pool's session and pull, so neither the pull nor the load merges into a store this build cannot correlate against: an `index.json` that is a bare array (format 1) or declares any `formatVersion` other than 2 is dropped whole — every `*.png` in the directory unlinked, the indexed signatures and the un-indexed `-raw.png` GGG crops alike, the index rewritten as `{"formatVersion": 2, "entries": []}`, and `pool-sync.json` left alone (`SyncFile::load` already discards a file from another format version). `load()` stays read-only. So on the first format-2 start the page shows ZERO learned template chips and "0 samples from the pool" until hovers and the next pull refill it, and the log carries one line — `Merc: dropped 61 format-1 template(s) (format 2)`, or `Merc: dropped an unreadable template index (format 2)` when the index parses as neither shape. `merc_reset_templates` writes that same v2 index shape, so the next start does not take a reset store for a stale one and unlink the PNGs a reset deliberately leaves on disk. POE-211 adds the first real MIGRATION beside that purge: samples stored under a family the alias table now folds are re-keyed in memory at `load` and written back once, rather than dropped — the format is unchanged, only the key is. `load` reports what it folded and stays a reader; the load seam does the write (`icons::persist_rekey`), and **the old family leaving `index.json` IS the one-shot marker** — no marker file, because one could disagree with the index it describes. The write runs AFTER the whole-store install and saves what the mutex holds, under `writing_icons_dir` → `merc_templates` — the order `apply_corpus` takes — so no forget or reset landing in the gap can rewrite an index naming the PNGs it then unlinks (`save` never unlinks, so nothing else ever would). It runs ONLY when the load reported no problems: the save rewrites `index.json` from memory, which omits an entry that would not decode — an AV lock, a OneDrive placeholder, a truncated PNG. The gate keeps THIS writer off the index on such a start; it does not protect the entry, because the first later save of the installed store (`apply_corpus`, `mark_uploaded`, the off-tick `SaveQueue`, a forget or a reset) drops it just the same — that erasure predates POE-211. What the gate buys is that the fold does not spend its one-shot marker on an incomplete read; art that is corrupt for good defers the fold on that device until `merc_reset_templates`. A re-keyed sample of the player's own that the pool had already accepted is reset to unpublished so it is offered again under the new family, and the OLD pool key is tombstoned: a tombstone is keyed `(version, family, tier)` with no device filter, so art nobody re-offers under the new name is retired for everyone. The seam only RECORDS those tombstones to `pool-sync.json`, and it records them whenever the load folded anything — on both arms of the save AND on a start that defers it, because the folded store is installed before either, so any later writer of it spends the marker — while `retry_pending_tombstones`, already running later in the same start, is what POSTs them (`record_pending_in` dedupes, so a deferred start that records again changes nothing). Recording takes the sync file's lock, never while the directory guard is held: the two locks are never held at the same time, here or in `apply_corpus`. The log carries one line — `Merc: re-keyed 1 sample(s) from Increased Area of Effect to Area of Effect (1 tombstone(s) offered)`, with `, N file(s) not removed` appended when an old PNG would not unlink.

**A confirmation costs two agreeing reads** (`run::fold_pending`, POE-207). The game's tooltip lags a moving cursor, so a hover tick that grabs the screen a frame after the cursor entered a new cell reads the PREVIOUS cell's tooltip over the NEW cell's crop — two "Ailment Damage" confirms landed one second apart on adjacent slots that way, and 19 of the 21 mislabels in the 2026-08-26 store came from that mechanism. A naming tooltip read is therefore only a CLAIM on `(row key, slot)`, carrying the cold crop as it stood at read 1; the next read decides it. Same key, same family AND tier: the claim is corroborated and applied — Confirmed, template learned from the claim's own crop, pool offer. Same key, different family or tier: the two reads disagree about one cell, so the fresh read replaces the claim and nothing is learned. A read on ANOTHER key is DISCARDED while the claim is younger than `TOOLTIP_LAG_BOUND` (2 s — the measured lag with margin, and a sweep is exactly a run of cross-cell reads inside it), and REPLACES the claim once it is older, because by then the tooltip on screen is the cell the cursor is actually in. A claim expires after `PENDING_CONFIRM_TTL` (10 s, stamped at read 1 and never refreshed, so it bounds the whole wait) or when its row key is absent from the current capture. `MATCHED_HOVER_ATTEMPTS` is 5 for that arithmetic: correcting a wrong `Matched` costs three charged reads — the fade-in miss that is always the first read of a hover plus the two that agree — a read the guard discards is refunded (`HoverBudget::refund`) so it costs nothing, and the remaining two are slack, not measurement. The post-grab cursor read is refunded on the same rule: it finds the cursor has LEFT the cell, throws the frame away before it costs an OCR, and so changes no state either. What it asks of the player is a DWELL on the cell — about a second, two 400 ms ticks — instead of a sweep across it. **A corroborated confirmation still does not always learn a template**: art the store already holds under a DIFFERENT family is refused (`TemplateStore::learn` returns `ConflictsWith`, and the log line names the key AND its provenance — `learned here` or `from the pool`, two different fixes). Storing one art under two families puts both permanently under `match_family`'s lead rule — neither can ever read `Matched` again, and a `forget` of either is a guess at which confirmation was wrong. The cell is still Confirmed, and the refused sample is never offered to the pool. The INCUMBENT wins on the learn path even against the player, because evicting a pooled sample this device cannot tombstone just invites it back on the next pull; `forget` on the named key is the escape, and it does tombstone. **The gate compares one unshifted signature against another** — sample-vs-sample, no alignment search, so a confirm stays cheap. That catches art byte-registered with the incumbent, which is the tooltip-lag case and 19 of the 21 samples the purge removed; it does NOT catch the same art cut from another cell rect or arriving from another device, which scores 0.45–0.70 unaligned. `merge_pulled` runs the same check on served samples, and resolves the collision by provenance: against a LOCAL incumbent the served sample yields, but two POOLED samples both go, because nothing here says which stranger is the mislabel and keeping either makes the surviving family a function of the server's listing order.

The pre-hover crop cache (`SigCache`) keys on `(row key, slot)`, the same identity a confirmation is stored under. Keyed on `row.index` it did not: the index is sequential over the rows one read found, so a dropped skill line renumbered every row below it and the crop looked up under the hovered cell was another cell's art, filed under the hovered cell's family — the second of the two mislabel paths. `row_key` is the row's skill id, falling back to its raw OCR text, and that fallback fails SAFE: a churned key finds no cached crop and the confirm reports `NoCrop` rather than learning the wrong art.

**Module start says what the matcher is running with.** One log line always carries the three icon thresholds in force — when a cell reads `?` that is the first question, and a log that only answers it when the numbers are unusual makes the usual case unanswerable — plus a warning when any threshold differs from the format-2 defaults, and another when `cellSize`/`cellInset` differ from theirs. `merc-geometry.json` stays the user's file and nothing here clamps it, but both blocks silently un-measure the matcher: the thresholds ARE the measurement, and the alignment window is cut out of `cellSize − 2·cellInset`, so a `cellInset` of 6 leaves a 25 px window that no longer reproduces the derivation every pooled signature was built from (every shared template stops matching), and 7 leaves 23 px, under `SIG_DIM`, where `icons::shift_window` gives up the alignment entirely. Both read as "the matcher stopped working" rather than as "I edited a geometry file".

Two committed ground truths hold the format down. `internal/mercenary/testdata/merc-sig-v2/` is the parity golden — a real 39×39 GGG cell crop and the 1728 bytes it must reduce to; the Rust test is the only writer (`MERC_SIG_UPDATE=1`, atomic temp-and-rename) and Go only reads, both suites compare against the same committed bytes, and the desktop container mounts the directory so there is exactly one copy. `desktop/src-tauri/tests/fixtures/merc-icon-crops/` is the 78-crop corpus — 78 raw 39×39 inner crops at scale 0.974 (61 harvested for POE-207, 17 from the laptop store for POE-209, the latter carrying a per-row `source`; the PC's store is a different geometry — scale 0.872, 34–35 px crops, POE-214 — and has never fed this corpus) with a manifest naming each one's family, tier, and whether the confirmation that produced it was WRONG (25 flagged poisoned, each with a reason). Every format-2 number is measured on the 53 clean crops: 17 same-family pairs, 15 of them clearing `icon_match` (weakest 0.924, median 0.9885), the two named hard pairs — `ailment-damage--t2` at 0.833 and `faster-projectiles--t2` at 0.855 — in the LowConfidence band, and no crop within `icon_match − icon_lead` of another family (worst 0.818, against a 0.83 ceiling). The four laptop crops that ARE poisoned are a different shape from the 2026-08-26 tooltip-lag purge: each carries art a family from the other store already holds (Faster Attacks/Faster Projectiles 0.880, Combustion/Ignite Chance 0.998, Ironwood/Physical as Extra 0.974, Secondary Shots/Extra Targets 0.998), which is POE-212's list. The perf gate is `#[ignore]`d and release-mode only — a wall-clock assertion in the ordinary suite is a flake generator — and measures the pool ceiling: 792 templates × 12 cells in ≈111–115 ms measured (two runs, 2026-08-27) of the 250 ms budget.

**Shared template pool** (POE-201, `src-tauri/src/mercenary/sync.rs`): the icon templates are pooled across devices, so one person's hover teaches everyone. The pool keys on the signature FORMAT (`FORMAT_VERSION` 2 since POE-207) and the serve path filters on the version the client asks for, so format-1 rows stay readable by format-1 clients and are never converted or deleted — the server ships FIRST, because a format-2 build against a server still on version 1 has every upload refused as an unsupported `format_version`. Four touch points on this loop, none of them on the capture tick:

- **Module start pulls the corpus.** `spawn_pull` fires before the local store is read, with the cached ETag as `If-None-Match` (a current copy costs 33 bytes of header). The loop then INSTALLS the loaded store into `merc_templates` and only afterwards waits up to 1.2 s for the corpus — install first, merge second, so every merge (this start's or a later task's) runs against the installed store under its mutex and no merge can be erased by a whole-store write behind it. The wait honours the module's cancel signal. Single-flight on the request; the SEAM claim is taken even when the request was not, because an off→on toggle across an in-flight pull is exactly the case where a corpus would otherwise apply itself against a store nobody had installed yet.
- **Opening a recruit window pulls again** (POE-210). `spawn_repull` fires on the `Captured` transition in `detect_tick`, so a hover made on another device reaches this one while both are still playing — with module start as the only trigger, seeing it meant restarting the module. Single-flight with the startup pull, and throttled to one ATTEMPT per 60 s measured from when the last one STARTED (`SyncState.last_pull_started_ms` — deliberately not the page's "checked N ago", which is stamped when a pull FINISHES and would let a device whose pulls all time out ask 20 s sooner every time). That throttle is what makes the trigger's noise free: a panel whose mercenary was REPLACED counts as a fresh capture, and so does a window the loop lost for two ticks and re-detected. An unchanged pool costs one 304 against the cached ETag. The re-pull never takes the SEAM claim — that flag is the load seam's, and setting it here would park the corpus for a seam that finished minutes ago and lose it.
- **A hover-learned signature is offered off-tick.** `enqueue` parks it and returns; the POST runs on a task in batches of 32 (a byte budget against the server's body cap, not against its stated ceiling of 64: one format-2 template is 1728 bytes, 2,377 wire bytes at the longest family name the vocabulary carries, so 32 of them is ~76 KB and `mercTemplateBodyLimit` went to 128 KB in the same change). Module start also offers every local sample the pool has not seen — the flag lives in `index.json`, so the retry is durable across restarts rather than bounded by one session. An acknowledgement that INVITES a retry (`capped`, `rejected_unknown_family`) leaves the samples owed, and so does a REFUSAL — but per SAMPLE, not per batch. The pool keeps one art under one family (POE-210): a template whose signature correlates at or above the server's `DedupeThreshold` with a LIVE sample of a DIFFERENT family is refused rather than stored, and the ack carries `conflicting` plus `conflicts[]` — the REQUEST position, the key, and the incumbent family — which the log turns into `Merc: pool refused <family> (tier N) — same art already pooled as <incumbent>`. The batch verdict is unchanged, so a NAMED refusal closes out the samples the pool did take and leaves only the refused one `uploaded: false` in `index.json`, offered again at the next module start. A refusal the desktop cannot place — `conflicting` with no `conflicts[]` behind it, an `index` of `-1`, an index the batch does not carry — settles NOTHING: no sample can be identified as the refused one, so the whole batch keeps `uploaded: false` and is re-offered next start, where whatever the pool really did store comes back `duplicate` and settles then. **First writer wins, and that is the accepted trade-off**: if the mislabel got there first, the correct art stays refused until somebody retires the wrong one. The fix runs on the device that learned it — forget that family (the ✕, which tombstones the key for everyone), and the refused art stores on that device's next start. Refusing at upload is still strictly better than the client-side merge rule alone (`merge_pulled` rule 3), which drops BOTH sides when both are pooled and so empties a good key on every device. **Deploy order**: the server change ships first AND the desktop tag in the same session — a format-2 desktop without the per-sample settlement marks a refused batch published whole, retiring on that device art the pool never took (blast radius: dev builds, since every released client is format 1 and is refused before the pool decides anything).
- **Forgetting a template tombstones it.** The ✕ posts a tombstone so pull-on-start cannot silently revert the forget, and records the key locally until the server acknowledges — while it is pending, the pull merges nothing for that key. Module start retries every unacknowledged forget. `merc_reset_templates` is local-only by contrast: it retires nothing for anyone, and its one server-facing effect is dropping the cached ETag so the emptied store does not get a 304. It writes the format-2 index shape rather than an empty file, so the purge above does not mistake a reset store for a stale one.

Every failure here is soft — an unreachable pool leaves the module fully working on local templates and costs ONE log line per module run, never one per attempt.

**Seeded from the gem art** (POE-208, `src-tauri/src/mercenary/seed.rs` + `seed-map.json`): a merc support icon IS the player support gem's inventory art, and the server already serves that art (`/api/gem-icon/{name}`, ADR-012), so the store can start out knowing some families before anyone hovers anything. `seed-map.json` is GENERATED and byte-pinned by its own test, never hand-edited: 51 of the 153 merc support families map to a gem (46 by `<family> Support`, 4 by `<family> Damage Support`, 1 by an explicit override — `Area of Effect`'s gem kept the pre-POE-211 spelling `Increased Area of Effect Support`), and every row carries the family's LOWEST vocabulary tier, so one seed lands under one `(family, tier)` key and every path keyed on the pair keeps working. **23 rows ship enabled** — the 22 whose art re-matched a clean corpus crop through the real matcher, plus Fork, compared by eye on 2026-08-27. POE-209's laptop crops flipped five families ON (Added Fire, Area of Effect, Chain, Multiple Totems, Pierce) and graded two more `corpus` that the pairwise rule then took straight back (Brutality, Maim). `name`-only rows ship DISABLED: a wrong seed is a confident wrong `Matched` that provokes no hover and feeds the verdict silently, so it never reaches the eviction rule, and the module's standing preference is to fail towards `LowConfidence` rather than towards a wrong family. So do both halves of any pair inside the lead band — Faster Attacks and Faster Projectiles (0.907 seed-to-seed; the FA seed reads an FP crop at 0.895), and Brutality and Maim (0.831, a thousandth over the 0.830 ceiling) — keeping one would answer the other's cells with a confident wrong name. A row can therefore grade `corpus` and still ship disabled, which is why the acceptance test re-checks the grade only on rows that ship and separately re-derives the exclusion behind the ones that do not. **Everything else still needs a hover**, exactly as before: the ~100 unmapped families, the merc-only ones with no gem counterpart at all (Archers, Additional Pods, Astral Totem…), and every `name` row until a curation ticket verifies it.

**A seed is local, disposable, and never wins.** `Origin::Seed` is never saved and never uploaded — `save()` skips it, `pending_uploads` skips it, and it is neither a learned nor a pooled key, so neither the learned list nor its pooled markers ever show it and an older build cannot read an origin it does not know (which would purge the whole store). Every start re-derives it from the cached art instead. It also yields to everything: installing skips a key another family already holds a sample under and a key already at `MAX_SAMPLES_PER_KEY`; a local confirm or a pulled sample that collides with a seed EVICTS it; a confirm of a seeded family stores a Local sample BESIDE the seed rather than being refused as "already known", so that family legitimately has a chip in two groups and two ✕ buttons that remove different things. **Every seed eviction blocklists the family** — confirm, pull, or ✕ — because the art is still in the cache and the next start would otherwise derive the same wrong seed again. `seed-blocklist.json`, beside the art cache, is the whole of the persisted seed state. The page's seed chip carries FAMILY NAMES, not `<family>--<tier>` keys (the key's tier is the map's, not a badge anyone read), and its ✕ calls `merc_forget_seed(family)`: local, blocklisting, and tombstone-free — nothing was ever offered to the pool, so there is nothing to retire for anybody else, and the chip's `title` says so rather than borrowing the learned chip's shared-consequence wording. `merc_reset_templates` clears the blocklist AND deletes `<app_data>/merc-icons/seed/`: a reset means start over, art included.

**The derivation is measured in fractions of the alignment window**, not in pixels — `SEED_ART_FRAC` 1.125 (art px per window px), `SEED_ART_OFFSET_FRAC` [4/34, −2/34], and `SEED_ART_BG` black, all three from an 8,580-point sweep against the corpus as it stood for POE-208 — 29 clean crops of mapped families — through the real matcher (26 matched, median best shift (0,0); the measured cell background (18,16,14) scored WORSE than black). POE-209 grew the corpus without re-running that sweep, which is `#[ignore]`d; the shipped constants are still held down by `the_shipped_calibration_matches_the_corpus_and_is_offset_sensitive`, now 17 of 32 clean crops clearing `icon_match` unshifted and a median best shift of (0,0). Fractions because art/window is scale-invariant while the window is not: 34 px at scale 1.0, 33 px at the live 0.974, and the ±3 px alignment search slides the probe rather than absorbing a resampling change. The seed is rendered into a synthetic cell of the geometry in force and passed through the same `normalize_cell` as everything else. Derived at module start against the window at scale 1.0 and RE-DERIVED — memoised on the window size in px, at most once per size per session, logged once — when a detect reports a different one (per plan: WI-B owns that hook).

**A cold cache costs one session, not the capture** (per plan — WI-B owns the fetch and the install seam). Art is fetched over the same route, SERIALLY, one request per enabled family with no cached file, and stored at `<app_data>/merc-icons/seed/<slug>.png` as served; a cached file is never re-fetched, which the route's `immutable` header is what justifies. Serial because a DEV server has no warm cache and fetches from poewiki live behind a 10 s timeout — politeness, and no startup stall. Every failure is soft and per family: unreachable, 404, 502 or a bad PNG leaves that family unseeded and retried next start, and none of them blocks a capture. On a warm cache the seeds are installed before the first detect; on a cold one the first detect can precede the fetch, so the first session after an install may still hover for a family the second gets for free.

**The art fixture is not committed.** The 51 poewiki PNGs the seed tests derive from are CC-BY-NC-SA and this repo is GPL-3 — the difference from the 39×39 corpus crops beside them, which are Sebastian's own screenshots. `make merc-seed-art` fetches them through the server route into `desktop/src-tauri/tests/fixtures/merc-seed-art/` (gitignored except its README, honours `POE_SERVER_URL`), and CI fetches from prod before `cargo test`. A test that cannot find them FAILS with that hint rather than skipping, because a silently skipped acceptance test is how a seed map stops being verified.

**Denylist**: PoE's own NPCs use the same speaker shape (24 measured, `Varashta, the Winter Sekhema` alone was 416 lines of one Client.txt), so the filter is a denylist, not a pattern. Shipped at `src-tauri/src/mercenary/assets/npc-denylist.txt`, extended without a rebuild by `<app_data>/merc-npc-denylist.txt` (one name per line, `#` comments, case-insensitive) — the same shape as `merc-geometry.json`. It is read once when the log watcher starts.

- **CONFIRM screen**: Shows 3 gem slots + CONFIRM button. Options list is gone. This is when gem tooltip OCR runs.
- `FontOpened` (`InstanceClientLabyrinthCraftResultOptionsList recieved`) fires in TWO moments: when the font is OPENED (CRAFT screen appears) and when CRAFT is CLICKED (CONFIRM screen appears). Opening the font, closing it for a stash trip, and reopening it therefore yields 3 events by the time CRAFT is clicked. Never derive CRAFT/CONFIRM parity or the round count from event count — the count is unbounded per craft. (Rule confirmed by Sebastian from play, 2026-08-18; earlier notes claiming "no event on open" were wrong.)
- Gem tooltips cover the font panel area when hovering — OCR regions overlap.
- **Mercenary voice lines** land in Client.txt as `<Name>, <joiner> <Epithet>: <text>`, and the speaker equals the recruit panel's header name. **The joiner is not always `the`** — `Fennik, of Unshakeable Faith` and `Swain, of Fractured Faith` are both measured mercenaries, so a `, the ` rule drops them silently. It must be LOWERCASE, which is what keeps `Alva, Master Explorer` (a two-part NAME, not a title) out without a denylist entry; the cost is that an NPC introduced with a lowercase joiner would need one. The name is `\S+` and admits a hyphen (`Al-Hezmin, the Hunter`) — a letters-only rule would put that NPC past the denylist that suppresses him. The lines also fire on approach and on click WITHOUT a window opening, so the line is a trigger, never a confirmation — the panel anchor still decides. Merc names are generated (first name × epithet); PoE NPCs use the same shape with fixed pairs, and player chat carries a `@`/`&`/`#`/`$`/`%`/`<Guild>` sigil instead. (Measured from Sebastian's Client.txt, 2026-08-25, rescanned with this shape: joiners `the` ×94 / `of` ×1, 25 NPC speakers shipped in the denylist, and the 70 speakers left after it are all generated merc names. ### Focus & Overlay

The focus poller (1s interval, `GetForegroundWindow`) uses three-state logic:
- **Game** (PoE foreground): show overlay
- **OwnWindow** (our process foreground): preserve state — no hide/show/status events
- **Other** (any other app): hide overlay

On the TRANSITION into **Game** it also resolves which display the game window is on (`MonitorFromWindow` → `AppState.game_monitor`, POE-237) and, when that changed, logs one line and emits `game-monitor-changed` to the main window. That owner is what `capture::capture_screen` grabs and what the layout builds each module's widget window on. Capture is the one other WRITER: a stored display xcap can no longer find is gone (unplugged, or rearranged out from under the rect), so it clears the owner, logs one line and grabs the primary — erroring instead stopped OCR for the rest of a session in which the player never made another focus transition. The transition is the whole cadence: a player who moves the game to another screen alt-tabs out and back to do it, so a per-second re-ask would spend a display enumeration on a question whose answer changes a handful of times a session.

Every overlay calls `set_overlay_clickthrough(label)` and is registered with the global `WH_MOUSE_LL` hook, which repairs the `WS_EX_TRANSPARENT` WebView2 strips off. Which clicks a window claims is a separate per-window declaration (`set_overlay_hot_rects` plus `set_overlay_has_content`, which `hit_test` reads FIRST): the comparator declares its button column and the trade-queue row, the temple's widget host declares whatever `[data-hot]` its widgets currently draw and arms the content flag from the same measurement (`overlay/widgets/use-hot-rects.ts`), compass/path-strip/timer/mercenary declare nothing and stay display-only; the capture/configuration overlay is intentionally interactive. Where two windows claim the SAME click, `hit_test` gives it to the most recently SHOWN of them (POE-239) — shown being the window's registration or the false→true EDGE in `set_overlay_has_content`, the only two show signals Rust gets, since the hook cannot read z-order inside `LowLevelHooksTimeout`; registration order is the tiebreak one monotonic counter cannot actually reach. Only the edge counts: the widget host sends the flag when emptiness flips, the comparator re-asserts `true` on every data change, and stamping a repeat would let a window nothing happened to out-rank one the user had just opened. A config-mode window is SKIPPED rather than ranked: config mode is exclusive by construction, the webview takes those clicks natively, so the hook has nothing to award and the skip must not be inverted. `set_overlay_hot_rects` logs one line per window pair per registration when two windows' rects collide — translated into SCREEN coordinates by each window's cached rect, since the declaring windows never share an origin, and skipped without being marked reported while either rect is unknown. The command logs the returned lines through `app_log`; `log::warn!` reaches nothing, because `env_logger` runs unfiltered with `RUST_LOG` unset and so drops everything below Error. The merc verdict overlay's click-through is load-bearing rather than cosmetic: `game_focused` (held over our own windows) decides overlay visibility while the merc capture loop gates on the RAW `game_in_foreground`, so a focused overlay would stop the loop it is displaying. See `docs/OVERLAY-GUIDE.md` for the current distinctions and regression guards.

## Screen Geometry (SSOT)

Normative. The data shape lives on `stores/ssot.svelte.ts` in the Stores table above; this is the lifecycle every module that measures or reads geometry follows (POE-214, POE-227).

**Lifecycle.** A measurement is remembered and TRUSTED at start — `settings::apply_to_state` loads the stored `screen_scale` back as `remembered`, and no module runs a blind sweep to re-derive it. It is VERIFIED by the consuming module on first use: the temple against `anchor::NCC_FLOOR`, merc against `cellfit`'s `SCALE_BAND`. `verifiedThisSession` (POE-240) is that second half made readable — true only while the value in force came from the merc gold frame in THIS run, false for a startup seed and for an OCR-only session — and it is never persisted, so every launch starts unverified. It also carries the blind spot the prune cannot see, an in-game UI-scale change made while no verifying panel is on screen: that is the temple's `FULL_READ_EVERY_N_MISSES` class, a stale value only a re-read catches, and the flag is what says so on the Settings card instead of the app pretending otherwise. (The prune's other blind spot, a different monitor of the same resolution, is closed since POE-237 — `screen_matches` compares the monitor id first and falls back to the dimensions alone only when either side is the unknown `0`.) It is dropped and re-measured on exactly three events — the capture's display or dimensions differ from the remembered ones (`ssot::drop_if_mismatched`, called first thing on every tick of the merc and temple detect loops — the gem/font OCR loops, the two debug capture commands and `mercenary::run::probe_tick` grab screens without it; the probe is harmless because it only asks whether recruit chrome is on screen and its answer never leaves the session — a hit hands the frame straight to the next full detect tick, which does check), the consuming module's verification fails, or the user presses **Recalibrate** in Settings (`ssot::geometry_recalibrate`). Nothing else re-measures, and a drop clears BOTH copies — the owner and `settings.json` — through `settings::persist_forgetting_screen_scale`, because the ordinary save path merges a stored value back over an empty projection.

**Recalibrate re-arms the modules; it does not merely empty the stores.** Neither module re-measures just because a store is empty — each holds its own copy for the life of a session, which is exactly why a wrong-but-self-consistent measurement survives both automatic checks and needs a button at all. So `ssot::geometry_recalibrate` does four things: it clears the shared screen scale in its owner, clears the temple's `AnchorCalibration` in ITS owner (`temple::run::clear_calibration`), bumps `temple_rearm` so the temple's read gate cannot skip the next board as unchanged, and bumps `merc_refit` so the merc detect tick drops the frame registration its session had SETTLED on (`run::consume_refit`, spent once and logged) before `held_is_stale` and `next_fitted_scale` run. Without that last bump the merc session would carry its held scale across the press and republish the forgotten number onto this slice on its very next tick. Then ONE settings write, `settings::persist_forgetting_screen_scale`, which rebuilds the file from `AppState` — both cleared owners included — with the screen scale explicitly emptied.

**Unit.** `1.0` is the 1920x1200 reference fixture, and 1080p measures 0.90 — the game's UI scales with screen HEIGHT, not width. The measurement, the captures it is taken from and the widget windows placed by it are anchored to the same display by construction (monitor id + origin, POE-237): the focus poller resolves the game's monitor from the PoE window's own HWND, `capture::capture_screen` grabs THAT monitor, the slice carries its id and origin, and `routes/(app)/+layout.svelte` builds each module's fullscreen widget window on it — so "window-relative physical px == capture px" is a fact about one screen rather than a coincidence that holds until the player drags the game to a second display. The temple's `AnchorCalibration.scale` is a DIFFERENT unit (its own 1374-px reference WIDTH) and the ratio between the two is unmeasured, so the two numbers must never be substituted for each other. Measuring that ratio is what `temple unit ratio k=…` in the app log is for: every full temple read prints `k = temple_scale / (capture_height / 1200)`, and until one live session's `k` is read off the log and committed as a constant, the temple does not write this slice. What is refused is a module OWNING its own calibration — measuring the screen for itself and answering a second, private version of this question. A validated unit-conversion coefficient over this slice's number (`k`) is the opposite of that: it consumes the one measurement instead of competing with it.

**Writer.** A measurement replaces the standing one only if `ssot::accepts` takes it (POE-240). `source` is a label describing the cue (`merc-frame` / `merc-ocr` / `remembered`), and the acceptance rule reads it rather than ranking it: a `merc-frame` reading always replaces; a `merc-ocr` one replaces only when it says something the drift cannot explain — a different display (POE-237), different dimensions, or a `ui_scale` further than 0.01 from the standing value (the documented 6-12 px OCR drift over the 1200-px reference height) — so an OCR tick cannot walk a session off a landed frame fit on the screen it is describing, while a reading from the monitor the game has just moved to is taken whatever the band says; a `remembered` seed fills an empty slot and never replaces anything. A refused measurement changes nothing at all, `measuredAtMs` included — the slice describes the value in force. There is still no precedence table to consult and none to add: that one rule is the whole contract.

| File | Exports | Description |
|------|---------|-------------|
| `geometry/view.ts` | `screenGeometryView(screen, now)`, `ScreenGeometryView` | The Settings "Screen geometry" card's five rows, derived from `ssot.screen`. Pure and separate from the card because its one rule is a rule about a MISSING value: an unmeasured screen renders as a REASON, never as a number, and never as 1.0 — which is a real measurement (the reference monitor) and would silently mis-scale every rect on a 1080p machine. `now` is passed in so the relative age ticks on the caller's clock and the function stays pure. |

**Placement.** A consumer expresses its rects in REFERENCE px and derives physical rects from `ui_scale`; it never hard-codes a resolution's pixels. There are two consumers. The widget geometry engine is the first: a widget it places from this slice is `anchored` — it carries no persisted position and no Settings row, because the game decides where it goes. The lab OCR `CaptureRegion`s are the second (POE-233): `lib.rs`'s `GEM_REGION_REF` and `FONT_PANEL_REF` hold the gem-tooltip and font-panel rects in reference px, `effective_region(user, reference, ui_scale)` is the one place the physical rect is derived, and a rect the user placed in Settings still wins over both. Their reference values are DERIVED, not measured — the shipped 1080p literals divided by 0.90 — and are provisional until both smoke machines confirm them; `ui_scale` is height-tied, so a non-16:9 monitor is an unverified case with no centring model behind it. `null` means nothing has measured a screen — a consumer must fail closed and MUST NOT substitute 1.0, which is a real measurement and would mis-scale every rect on a 1080p machine by 11%. The lab regions are the ONE documented departure and it is not a substituted scale: with no measurement they **assume 1080p**, which is precisely the rect the app cropped before POE-233, because a widget that fails closed is merely not drawn while an OCR loop that fails closed reads nothing at all. Each scan loop says so once per session in the app log, so the assumption is visible rather than silent.

## Conventions

- **Stores**: `.svelte.ts` extension (Svelte 5 runes). Export objects, mutate properties (NOT reassign).
- **Components**: `.svelte` files in `components/`. Props via `$props()`. Scoped styles.
- **Utilities**: `.ts` files. Pure functions, no reactivity.
- **Styling**: CSS custom properties from `src/tokens.css` (`--bg`, `--surface`, `--border`, `--text`, `--text-muted`, `--accent`, `--success`, `--warning`, and the `--color-lab-*` palette). `tokens.css` is the only declaration site: `app.css` `@import`s it and adds the document reset and an OPAQUE `body` background, so the main window imports `app.css` while `routes/overlay/+layout.svelte` imports `tokens.css` ALONE — an overlay window must stay transparent. A component shared by both (`temple/TempleLattice.svelte`) therefore resolves the same colours in each; `overlay/overlay-tokens.test.ts` fails if it stops being true — it globs EVERY `routes/overlay/*/+page.svelte` plus the components drawn in them, so a new overlay route is covered the day it lands.
- **Tauri commands**: Use `invoke()` from `@tauri-apps/api/core`. Follow the established event, command, or reconciliation mechanism for the state path being changed.
- **State flow**: Shared status is event-driven, while comparator and some overlay settings/layout paths poll or reconcile against Rust/server state. Do not introduce duplicate owners.
- **Settings persistence**: `%AppData%/profitofexile/settings.json`. Saved automatically on every mutation.
- **Logging**: `%AppData%/profitofexile/app.log` (persistent) + in-memory buffer (50 entries, UI).
- **DPI**: Comparator overlay uses `PhysicalPosition` via Rust `move_overlay` — no DPI conversion. OCR region overlays use `scaleFactor()` for constructor coords. Never use `devicePixelRatio` in overlay WebViews.
- **Error handling**: Log errors to `app_log`, never silently discard. Throttle capture loop errors.
- **Relative time**: `formatTimeAgo` now exists in three places — `routes/(app)/components/Header.svelte`, `components/TradeListings.svelte`, and `exchange/view.ts` — each with its own wording. The second home moved out of `Comparator.svelte` with the listings table (POE-202) and is now shared by both of that table's consumers. Extracting one shared helper is a follow-up, not a rule any of the three currently follows.

## Migration Notes (web → desktop)

When migrating components from `frontend/src/routes/lab/`:
- Replace `fetch('/api/...')` with `invoke('command_name', { args })` for Tauri commands
- Replace Svelte 4 stores (`$store`) with Svelte 5 runes (`$state`, `$derived`, `$props`)
- Replace `export let` props with `let { prop } = $props()`
- Replace `<slot />` with `{@render children()}`
- Replace Tailwind classes with CSS custom properties (`var(--accent)`, etc.)
- Data from Go server API: use `fetch()` against `store.status.server_url` base URL
- Mercure SSE: same pattern as web (`EventSource` to server's Mercure hub)
