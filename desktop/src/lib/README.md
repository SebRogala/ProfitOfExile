# Desktop App Library (`$lib`)

Component registry for the ProfitOfExile desktop app. Read this first before creating or modifying components.

## Stores

| File | Export | Description |
|------|--------|-------------|
| `stores/status.svelte.ts` | `store`, `initStatusStore()` | Shared app state — event-driven from Rust backend. No polling. Call `initStatusStore()` once from root layout. Read `store.status` and `store.logs` reactively. |
| `stores/ssot.svelte.ts` | `ssot`, `startSsotStore()`, `stopSsotStore()`, `fetchSsot()`, `applySnapshot()`, `setNormalVariant()`, `setDedicationVariant()`, `setDedicationPool()`, `setDedicationSelection()`, `setModuleEnabled()`, `setTempleKeys()`, `setTempleConfig()`, `setTempleProfile()`, `rearmTemple()`, `templeDebugCapture()`, `SsotSnapshot` | Rust-owned single source of truth, polled every 3000 ms (`ssot-changed` is only an eager nudge — never trusted as the payload). Read `ssot.league` / `ssot.normalVariant` / `ssot.dedicationVariant` / `ssot.dedicationPool` / `ssot.modules` reactively; write through the exported setters (never assign the fields directly or keep a local copy). Market fields and module flags carry a poll-vs-write ordering guard; the two module SLICES do not, because nothing here writes them. `ssot.mercenary` (POE-165) is the Merc OCR slice — status, last capture, learned templates, last error, geometry source. `ssot.temple` (POE-171) is the temple builder slice — status, layout, side panel, advice, mode, and the settings echo (`keys` / `config` / `profile`). Both are read-only and apply the same way: a snapshot carrying the slice replaces it WHOLE, one lacking it leaves the last known one standing. The five `temple*` writers go through Rust commands that write `temple_settings`; Rust echoes the accepted value onto the slice and the setter re-fetches, so there is no optimistic local value. They return the rejection message (`string | null`) instead of throwing, and a rejection also reaches `app_log_from_frontend` — Rust VALIDATES these, unlike the market setters whose only failure is IPC. |
| `stores/navigation.svelte.ts` | `nav`, `viewToPath()`, `parseView()`, `VIEW_PATHS`, `View` | Global view toggle. `nav.view` is `'lab' \| 'settings' \| 'dev' \| 'mercenaries' \| 'temple' \| 'currency-exchange'`. All pages are always mounted (hidden via CSS) — do not use SvelteKit routing for main views because it unmounts their listeners. `viewToPath(view)` gives the Sidebar path for a view (`'lab'` → `'/'`); use it instead of re-deriving the mapping, and add a `VIEW_PATHS` entry when adding a view — `go()` inverts that table, so there is no second mapping to extend. The pick is the persisted `navView` pref (ADR-013), so the app reopens on the last tool: `nav.view` is a GETTER over the pref (validated on read through `parseView`, unknown → `'lab'`) and `nav.go(path)` writes it — never assign `nav.view`. Restore-on-launch and "a click made before the prefs load lands beats the stored value" both come from `persisted()`'s own dirty-flag semantics, not from a restore step here. |

A direct play has no convert step and the slot stays — an empty dashed tile in comfortable, the fixed-width “not used” label alone in dense — so a column always holds the same kind of step and the eye can run down it. Since POE-193 the row is the whole worthwhile RUN. Steps 1 and 2 read as whole-quantity ORDERS — `buy 12 for 420c`, `sell 12 for 3 div` — rather than the per-unit decimal the in-game exchange has no field for; the rate span's `title` is `rateTitle` when the printed quantity is not the one the step was asked for and the rate STRING otherwise, because `.slot` clips its fixed width and the tail it drops is the unit word. Deciding it per row would put a collapsed row's Get under the next row's sell, which is what the fixed geometry exists to prevent. Presentation only — every string, icon path and flag comes from `routeSlots`, and a play it answers `null` for renders an empty route cell rather than dropping the row. |

The sixth is POE-196's **Min item price**, first in the row and the only default-on filter in the app: it leads because it is the one box already doing something when the row is first opened, so a reader who came to find out why a sub-chaos play is missing meets it before the five that are empty. | `components/ExchangeItemPicker.svelte` | `items`, `categories`, `categoryRules`, `itemRules`, `apiBase`, `anchor` (default `null`), `oncategoryrule`, `onitemrule`, `onclose` | The filter bar's "Add" popover (POE-186) — the category pills on top, a search box over display names, one row per item of the current response's plays. `anchor` is the toggling control counted as part of the popover for dismissal: without it a pointerdown on Add reads as "outside" and closes the popover on the same click that is opening it, losing the typed query (Escape also closes; `null` leaves the popover itself as the whole root). Every `parse*` is the read-side validator for one persisted pick (ADR-013), so a preference from an older build degrades to a default instead of throwing on first render. `deriveState()` is the single owner of the header's five states, including the rule that an error outranks `warming`; `dataAgeParts()` dates the table from the settled hour's `to`, never from `lastUpdated`, because the feed publishes 40-60 min after the hour closes and only the first answers "how stale are these prices". `formatRoiPct()` takes a FRACTION (exchange ROI, unlike the gem side's percentage points) and `formatGain()`/`formatChaos()` take their sign from the *rounded* magnitude, so a move too small to print is never dressed as one. Chaos AMOUNTS are INTEGERS (POE-189) — `formatChaos`/`formatGain` round to whole orbs on the magnitude and sign afterwards, so a gain and the identical loss round the same way, and a sub-1c figure prints an unsigned `0` (the signed-zero rule); the fractional decimals belonged to the leg RATES, and since POE-193 those are whole-quantity orders too — `formatLegPrice` survives as the version-skew fallback below. `worthwhileScale(play)` (POE-192) is how far a play must be repeated to be worth doing: `flips = ceil(SCALE_TARGET_CHAOS / expectedRoi)` — 100c, an OWNER CONSTANT and not a preference, because the app derives the size so the reader types none — with the scaled `gain` and `investment` those flips are expected to pay and to tie up (`gain` is reported, not assumed to be 100: a 3c expectation clears the bar at 102c), and `hours = ceil(flips / depth)`, deliberately OPTIMISTIC (the whole market's hourly volume, no competition) and UNCAPPED — the wait IS the warning; `hours` is `null` when the thinnest leg traded nothing. It counts the SIMULATED expectation and not the optimistic `roi` since POE-193, because the per-hour figure overstates the realized outcome 4-8x and scaling on it answered with a flip count the play would never have paid off at. The whole answer is `null` for `expectedRoi <= 0` — and unlike the `roi <= 0` this used to read, that is a case the table HITS: ADR-015's positivity floor governs the optimistic pair, while the fill simulation is free to measure a loss and ADR-016 serves and flags the play anyway, so the Scale column shows a dash rather than advice a losing expectation has no answer to. `sortPlays(plays, sort)` keeps every suspect play after every clean one whatever its ROI or wait — the flag is the reason it ranks last — and leaves the `expected` order exactly as served rather than re-sorting away the server's tie-breaks (the low-coverage band above all, which no single number reconstructs); the `fastest` order is `worthwhileScale().hours` ASCENDING with `null` last in its partition, stable, and it ties often because the hours are whole ones — everything absorbed inside the hour reads 1 and keeps the server's order behind that. `parseSort` maps two stored spellings FORWARD rather than defaulting them, because in both cases the order the reader picked still exists under a new name: `'fill'` → `'fastest'` (the deleted Quantity era's `fillHours` was the same fastest-to-absorb ask) and `'roiPct'` → `'expected'` (that pick always meant "the list as the server ranked it", and POE-193 re-based the ranking on `expectedRoi`). `routeSlots(play, divineChaosRate)` reads the five slots off leg POSITION, not `action` (the third leg is a wire `sell` and a *convert* on screen), and since POE-193 it draws the whole worthwhile RUN rather than one exchange. Three rules it now holds to, each a fix for a live misreading: (1) EVERY STEP NAMES THE THING IT ACTS ON — all three take `itemName`/`itemIcon`, where step 2 used to take the sell leg's QUOTE and so put "Divine Orb" and the divine artwork beside the SCARAB's price; (2) EVERY RATE IS A POSTABLE ORDER CARRYING ITS UNIT. The unit is `quoteUnit()` — `c` / `div`, and `''` for an id that is neither, so an unchecked currency prints a bare number instead of a wrong label — because a route entered in divine otherwise read chaos → chaos → chaos with the divine nowhere on the row; the QUANTITIES are the leg's `priceItemQty`/`priceQuoteQty` pair (POE-193, exactly the leg's `price`) rather than that decimal, because the in-game exchange trades whole quantities on both sides and has no field for a per-unit price — `sell @ 0.25 div` was an instruction the reader could not carry out, and the same trade posts as `sell 4 for 1 div`. Steps 1 and 2 scale the pair by the largest whole multiple that fits, so the quantity shown is always `integer × pair` and therefore expressible in game; a target the lot does not divide SNAPS the displayed quantity down to the largest one that is (12 on a 5-for-2 market shows `10 for 4 div`) and fills `RouteStep.rateTitle` with the reason, the ends keeping the true run arithmetic. The two steps do NOT snap independently: the traded quantity is derived ONCE, buy-first — step 1 snaps against the buy market's lot and step 2's target is then what step 1 actually BOUGHT, because the reader can only sell what they hold, and independent snaps printed `buy 48 for 3 div → sell 50 for 5 div` on a single fixture. Whatever step 2's own lot cannot cover stays in the stash (48 bought on a ten-for-one-divine market sells 40) and never touches the ends; a buy leg that fell back to the decimal posted no quantity, so the sell step targets the run itself. The one case where step 2 exceeds step 1 is a target under a single lot, where the floor would be zero: the step posts one whole lot and `rateTitle` says it OVERSHOOTS — the two titles are branched, because the undershoot's "the ends still count the whole run" is false when the order is the larger of the two. Both titles are told against the TARGET (the quantity that step was asked to move, which on step 2 is what step 1 bought) and name the run only where it is a second number; the undershoot adds "N of the M bought stay unsold" whenever the target is bought stock, keyed on `RunOrder.bought` rather than on `target !== run`, since the residue is the same fact whether or not the buy lot happens to equal the run. The scale-null branch fills BOTH steps' `rateTitle` with a note of its own: there is no run to scale toward, so each step falls back to one lot of its own market, and a row reading `buy 1 for 35c → sell 4 for 1 div` otherwise shows a 4:1 divergence that is no snap and that nothing on screen explains — the note claims no mismatch, only that the counts agree where the two markets happen to post the same lot, and it is withheld from a step whose pair was missing (a decimal shows no lot to explain) and from step 3, whose bare pair is what a convert always shows. Step 3 passes no run and prints the BARE pair, since what a convert moves is the sale's proceeds and no whole count of anything; its item side carries a unit word because the intermediate IS a currency, where a scarab's does not. The pair is the hour's PRINTED extreme and not the order to post — the one that fills sits a step tighter, which the end amounts already pay for — so every claim in the copy is about the FORM (a whole-quantity order rather than a per-unit price the exchange has no field for) and never "place this order"; a leg whose pair is absent or not a positive integer pair falls back to the decimal rate, unit and all, the reachable cause being VERSION SKEW rather than a stale cache, since this app holds no response cache but does point at a configurable server; (3) THE ENDS ARE IN THE ENTRY CURRENCY, the buy leg's quote, since `investment`/`roi` are chaos figures whatever the legs are quoted in and a divine-entry play printed "spend 14 chaos" beside a divine-denominated flow. Spend is `worthwhileScale().flips × price × (1 + tick)` — the same derived size the Scale column prints and the Run cost bounds measure, at the UNDERCUT entry `investment`/`expectedRoi` are already priced at, never rebuilt from the raw `price` alone — with the chaos reading as a sub-line, taken from `worthwhileScale().investment` directly rather than re-multiplied, that being the exact figure the filter bar's Run cost bounds compare against; Get is Spend plus `scale.gain` converted into that currency, over a `keep ≈ Nc` profit line (plus the `(≈ 0.xx div)` equivalent on a divine entry). Chaos amounts stay whole orbs and non-chaos ones go through the private `formatFractionalOrbs` — hand-grouped, always to the hundredth — a run in divine routinely costing a fraction of one and `formatLegPrice` being wrong for a TOTAL, since its `toFixed(0)` above 100 would print a 101.25-divine run as "101" and its 101.75 return as "102", moving the total by four times the half-divine profit line under it. Both end tiles carry a BUILT `currencyIconPath(quote)` rather than artwork scavenged off `quoteIcon`, which left a play's ends as two empty tiles (POE-189). Two fallbacks, both live-ish: a play with no positive expectation has no run size, so the ends drop to the per-exchange `investment`/`investment + roi` chaos figures the wire guarantees while the units and item icons stay — and `positive` follows the `roi` those ends are built from rather than the expectation, because the flag styles the numbers ON SCREEN and that Get is visibly the larger of the two (the measured verdict is carried by the red Exp. The page passes the one answer to every `ExchangeRoute` and to its own header spans, because both carry the same fixed slot widths and must collapse together; per-row would slide a collapsed row's Get under the next row's sell. Empty list answers false — unobservable (no rows, no table) and the honest one of the two. `refetchDelay()` owns the Mercure debounce + jitter, the same two values `LabPage.svelte` runs against the same publish. `iconSrc()` (POE-177) joins the API base onto a leg's API-relative `itemIcon`/`quoteIcon` path — the server serves that artwork from its own cache because production cannot reach poewiki (ADR-012) — and answers `null` for both `null` and `""`, since an empty path joined onto the base requests the base itself. ## OCR Lifecycle

Two decoupled scan loops, each on a dedicated OS thread (required by Windows COM/WinRT).

Every crop is contrast-stretched and upscaled 2× before recognition (`capture.rs::preprocess_for_ocr`) — no size gate: crop dimensions say nothing about the glyph height inside them, and a font panel region widened for a high-resolution client was the case an earlier height gate skipped. The recognizer is pinned to en-US because the PoE client renders English whatever the Windows profile locale says. When that pack is missing, each scan thread falls back to the profile language and OCR degrades silently, so the warning is cached process-wide (`ocr.rs`) and surfaced as `AppStatus.ocr_language_warning` — the engine itself is thread-local and `build_status` must never resolve one. Every scan thread emits the status once when it starts and finds a warning cached, rather than only the thread that cached it: a debug command can resolve the engine first and has no status to emit, and the scan's own pre-spawn emit runs before any engine exists.

### Gem Tooltip OCR

Scans the gem tooltip region to detect transfigured gem names for the comparator.

**Start triggers** (all: clear comparator, restart scan):
- `FontOpened` — Client.txt `InstanceClientLabyrinthCraftResultOptionsList recieved` (fires on font open AND on CRAFT click — see Game UI facts below)
- Manual "Start Scanning" button

**Stop triggers**:
- 3 gems detected (auto-stop)
- 45s timeout
- ZoneChanged (left area)
- Manual "Stop Scanning"
- Next start trigger (bumps generation counter → old scan exits)

**Key behavior**: Aborts immediately if gem name list is empty (server unreachable). Uses `AtomicU64` generation counter for clean cancellation — no thread cleanup needed.

### Font Panel OCR

Scans the font region to capture craft options (transform, quality, experience, etc.) from the CRAFT screen.

**Start**: Izaro death voiceline (`LabFinished` nav event) — triggers when final Izaro is killed, right when the font becomes available. A `FontOpened` event also starts a scan whenever the liveness token (`font_scan_live_gen`) reads 0, so the panel is still read when `LabFinished` was never seen — the app launched mid-run, or the scan was stopped earlier by a zone change or lab exit.

**Running**: Scans at 250ms, parses options via `font_parser`, then union-merges the frame into the current round's option buffer (`merge_options`). A torn frame never deletes an option an earlier frame of the same panel read, and a value already read is never downgraded to `None` or overwritten by a disagreeing later read.

**Round tracking**: the panel's "Crafts Remaining" count owns the round boundary (`font_ledger`), gated on a `FontOpened` counter. `FontOpened` seals nothing — it fires on font open as well as on CRAFT, an unbounded number of times per craft. A count change with no `FontOpened` since the last accepted count is a misread: the frame's options still merge, the count is ignored. A count change after a `FontOpened` that holds for 2 consecutive frames seals the current round under the *old* count and opens the next one; direction is irrelevant. Known limitation: a round on screen for under 2 frames (~500ms) is never accepted, so its options fold into the neighbouring round.

**Stop**: a `font_scan_generation` bump — ZoneChanged, `LabExited`, a replacement scan, app shutdown — or 10 minutes with no active font panel on screen. There is no wall-clock timeout: a font run has no bounded length (stash trips, town portals, a player reading the options), and a scan expiring under a still-open panel silently lost every remaining craft. The idle limit measures from the last frame that saw the panel, so it only fires on a scan with nothing left to read — it is the backstop for a run whose stop event never arrives (the game killed rather than exited, the font never opened, screen capture failing in a loop). That path sends the session itself; every other stop is either a sender or is followed by one.

**Re-arm**: the token is what makes that restart exactly-once — a scan claims it on spawn and releases it on exit with a compare-exchange, so a superseded loop cannot clear its replacement's claim and a `FontOpened` arriving mid-handover does not stack a second loop. The case that needs it most is a portal trip out of the lab: `LabFinished` never fires again on return, so without the re-arm every remaining craft is lost. Every stop that can have rounds behind it sends and resets the session before a re-arm can run: ZoneChanged does it on the send path (and fires on the same log line as `LabExited`, which only stops the loop), idle expiry does it from inside the loop. So a re-armed scan is always a new segment; a mid-font town trip therefore reports one run as two font-session POSTs.

**Data flow**: ZoneChanged sends accumulated session (all rounds with options + crafts_remaining) to server via `POST /api/desktop/font-session`.

### Game UI Context

- **CRAFT screen**: Shows options list + "Crafts Remaining: X" + CRAFT button. "Crafts Remaining" only visible when X > 1.
- **CONFIRM screen**: Shows 3 gem slots + CONFIRM button. Options list is gone. This is when gem tooltip OCR runs.
- `FontOpened` (`InstanceClientLabyrinthCraftResultOptionsList recieved`) fires in TWO moments: when the font is OPENED (CRAFT screen appears) and when CRAFT is CLICKED (CONFIRM screen appears). Opening the font, closing it for a stash trip, and reopening it therefore yields 3 events by the time CRAFT is clicked. Never derive CRAFT/CONFIRM parity or the round count from event count — the count is unbounded per craft. (Rule confirmed by Sebastian from play, 2026-08-18; earlier notes claiming "no event on open" were wrong.)
- Gem tooltips cover the font panel area when hovering — OCR regions overlap.

### Focus & Overlay

The focus poller (1s interval, `GetForegroundWindow`) uses three-state logic:
- **Game** (PoE foreground): show overlay
- **OwnWindow** (our process foreground): preserve state — no hide/show/status events
- **Other** (any other app): hide overlay

The comparator uses selective click-through (`WS_EX_NOACTIVATE` + `WS_EX_TRANSPARENT`) with a global `WH_MOUSE_LL` hook and a right-edge interactive zone. Display-only compass/path-strip/timer overlays use `interactiveWidth: 0`; the capture/configuration overlay is intentionally interactive. See `docs/OVERLAY-GUIDE.md` for the current distinctions and regression guards.

## Conventions

- **Stores**: `.svelte.ts` extension (Svelte 5 runes). Export objects, mutate properties (NOT reassign).
- **Components**: `.svelte` files in `components/`. Props via `$props()`. Scoped styles.
- **Utilities**: `.ts` files. Pure functions, no reactivity.
- **Styling**: CSS custom properties from `src/tokens.css` (`--bg`, `--surface`, `--border`, `--text`, `--text-muted`, `--accent`, `--success`, `--warning`, and the `--color-lab-*` palette). `tokens.css` is the only declaration site: `app.css` `@import`s it and adds the document reset and an OPAQUE `body` background, so the main window imports `app.css` while `routes/overlay/+layout.svelte` imports `tokens.css` ALONE — an overlay window must stay transparent. A component shared by both (`temple/TempleLattice.svelte`) therefore resolves the same colours in each; `temple/overlay-tokens.test.ts` fails if it stops being true.
- **Tauri commands**: Use `invoke()` from `@tauri-apps/api/core`. Follow the established event, command, or reconciliation mechanism for the state path being changed.
- **State flow**: Shared status is event-driven, while comparator and some overlay settings/layout paths poll or reconcile against Rust/server state. Do not introduce duplicate owners.
- **Settings persistence**: `%AppData%/profitofexile/settings.json`. Saved automatically on every mutation.
- **Logging**: `%AppData%/profitofexile/app.log` (persistent) + in-memory buffer (50 entries, UI).
- **DPI**: Comparator overlay uses `PhysicalPosition` via Rust `move_overlay` — no DPI conversion. OCR region overlays use `scaleFactor()` for constructor coords. Never use `devicePixelRatio` in overlay WebViews.
- **Error handling**: Log errors to `app_log`, never silently discard. Throttle capture loop errors.
- **Relative time**: `formatTimeAgo` now exists in three places — `routes/(app)/components/Header.svelte`, `Comparator.svelte`, and `exchange/view.ts` — each with its own wording. Extracting one shared helper is a follow-up, not a rule any of the three currently follows.

## Migration Notes (web → desktop)

When migrating components from `frontend/src/routes/lab/`:
- Replace `fetch('/api/...')` with `invoke('command_name', { args })` for Tauri commands
- Replace Svelte 4 stores (`$store`) with Svelte 5 runes (`$state`, `$derived`, `$props`)
- Replace `export let` props with `let { prop } = $props()`
- Replace `<slot />` with `{@render children()}`
- Replace Tailwind classes with CSS custom properties (`var(--accent)`, etc.)
- Data from Go server API: use `fetch()` against `store.status.server_url` base URL
- Mercure SSE: same pattern as web (`EventSource` to server's Mercure hub)
